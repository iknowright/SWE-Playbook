Instruction Set Architectures: x86-64 vs. ARM64 & Operating System ABIs

11.0 The ISA Boundary & The Silicon Contract

Every software engineer ultimately relies on a compiler to translate human-readable syntax (C++, C#, Rust) into binary machine code. But what exactly dictates the rules of that binary? The answer is the Instruction Set Architecture (ISA).

The ISA is the absolute, immutable legal contract between the software compiler and the physical silicon. It defines the exact binary vocabulary the CPU understands: the registers available, the memory addressing modes, the supported data types, and the precise bit-level encoding of every operational opcode.

However, the ISA is just an interface. How the CPU implements that interface is called the Microarchitecture. AMD and Intel both use the same ISA (x86-64), allowing them to run the exact same Windows binary executable. Yet, their internal silicon microarchitectures (Zen 4 vs. Raptor Lake) are radically different, utilizing different Branch Predictors, L1 caches, and Out-of-Order (OoO) schedulers to execute that same binary.

CISC vs. RISC Genesis

The computing world is currently split by a holy war between two fundamentally opposed ISA philosophies: CISC (Complex Instruction Set Computer) and RISC (Reduced Instruction Set Computer).

  • CISC (x86-64): Born in the 1970s when RAM was incredibly expensive. To save memory, Intel engineers designed variable-length instructions where a single dense, complex byte-sequence could perform multiple operations simultaneously (e.g., fetch from memory, add a register, and store back to memory). The philosophy: Make the hardware complex to keep the compiled software small.
  • RISC (ARM64): Born in the 1980s. Engineers realized that complex instructions were impossible to pipeline efficiently. They stripped the ISA down to uniform, fixed-length 32-bit instructions that only perform one task. The philosophy: Make the hardware simple and uniform so it can run at blistering gigahertz frequencies, and shift the burden of complexity to the software compiler.
The Microcode Illusion (Indigo)
Modern x86-64 processors are not actually CISC under the hood. To achieve deep superscalar pipelining, Intel and AMD CPUs contain massive hardware decoders that intercept the complex, clunky x86 CISC assembly instructions and dynamically translate them into Micro-operations ($\mu\text{ops}$). These $\mu\text{ops}$ are essentially proprietary RISC instructions executed by the hidden OoO core. An x86 CPU is a RISC engine trapped inside a CISC emulator.

11.1 The x86-64 Philosophy (CISC)

The x86-64 architecture (originally invented by AMD and dubbed AMD64) is the undisputed king of the desktop and server datacenter. However, it is an architecture built on 45 years of continuous, unbroken backward compatibility.

The Weight of Evolutionary Baggage

When you boot a modern Intel Core i9 or AMD Ryzen threadripper, it does not wake up as a 64-bit monster. It wakes up in 16-bit Real Mode, behaving exactly like a 1978 Intel 8086 processor. The OS Bootloader must execute specific assembly instructions to transition the CPU into 32-bit Protected Mode, and finally into 64-bit Long Mode.

Because Intel refused to break backward compatibility, the modern x86-64 silicon die is permanently scarred with legacy decoders and bizarre architectural quirks required to run 40-year-old MS-DOS software.

Variable-Length Chaos

The defining characteristic of x86-64 is its variable instruction length. An x86 instruction can physically range from 1 byte to 15 bytes.

; 1-Byte Instruction
C3              ; ret (Return from subroutine)

; 2-Byte Instruction
31 C0           ; xor eax, eax (Zero out EAX)

; 7-Byte Instruction
48 8D 05 F1 2A 00 00  ; lea rax, [rip + 0x2af1] (Load Effective Address)

This variability provides incredible Code Density. An x86 binary is often 30% smaller on disk than an equivalent ARM binary, meaning it consumes significantly less L1i Cache space. However, this density causes a nightmare for the Instruction Fetch (IF) pipeline stage: the CPU has absolutely no mathematical way of knowing where the next instruction begins without fully decoding the current one.

Memory-to-Register Operations

Unlike RISC, x86 breaks the strict Load-Store paradigm. It permits instructions that execute math directly against main RAM addresses.

; x86 CISC Macro-operation
add dword ptr [rcx], 5

This single instruction instructs the CPU to compute a pointer, fetch 4 bytes from the L1d cache, route them to the ALU, add 5, and write the result back to the L1d cache. Under the hood, the hardware decoder shatters this into three distinct $\mu\text{ops}$ (LOAD, ADD, STORE) to feed the pipeline.

11.2 Anatomy of an x86-64 Instruction (Hex-Level LLD)

To understand the pain of the x86 hardware decoder, we must dissect the binary format. A maximum-length x86 instruction consists of six optional parts:

[Prefixes] [Opcode] [ModR/M] [SIB] [Displacement] [Immediate]

1. The Prefixes (1 to 4 Bytes)

Prefixes modify the default behavior of the opcode. When AMD created the 64-bit extension, they needed a way to access the 8 new registers (R8-R15) and specify 64-bit operand sizes. Instead of creating thousands of new opcodes, they hijacked a block of single-byte opcodes (0x40 to 0x4F) that were previously used for 32-bit `INC/DEC` instructions and repurposed them as the REX Prefix.

  • REX.W (Bit 3): If 1, promotes the operation to 64-bit.
  • REX.R (Bit 2): Extends the ModR/M register field to address R8-R15.
  • REX.X (Bit 1): Extends the SIB index field.
  • REX.B (Bit 0): Extends the ModR/M base field.

2. The ModR/M Byte (The Addressing Engine)

If an instruction takes operands, the ModR/M byte dictates where they live. It is sliced into three bitfields: [Mod: 2 bits] [Reg: 3 bits] [R/M: 3 bits].

  • Mod (Mode): Dictates if the operand is a direct register, or a memory pointer with a 0-bit, 8-bit, or 32-bit displacement.
  • Reg: The 3-bit ID of the destination register (e.g., 000 = RAX, 011 = RBX).
  • R/M: The 3-bit ID of the source register or memory base.

3. The SIB Byte (Scale-Index-Base)

If the ModR/M byte indicates complex array addressing, it is immediately followed by a SIB byte. This is x86's hardware math engine for loops. It encodes [Base + Index * Scale].

  • Scale (2 bits): Multiplier of 1, 2, 4, or 8 (perfect for array element sizes).
  • Index (3 bits): The register holding the array index.
  • Base (3 bits): The register holding the array's starting memory address.

The Full Translation Target

Let's manually assemble the complex instruction: add qword ptr [rcx + r8*8 + 0x10], rax

This adds the 64-bit value in RAX into the memory address at RCX + (R8 * 8) + 16.

  • REX Prefix: We need 64-bit width (W=1). We are using R8 as an index (X=1). We are using RCX as base (B=0) and RAX as source (R=0). 0100 1010 → 0x4A.
  • Opcode: 64-bit ADD mem, reg → 0x01.
  • ModR/M: Mod=01 (8-bit displacement). Reg=000 (RAX). R/M=100 (Indicates a SIB byte follows). 01 000 100 → 0x44.
  • SIB Byte: Scale=11 (Multiplier of 8). Index=000 (R8, extended by REX). Base=001 (RCX). 11 000 001 → 0xC1.
  • Displacement: 16 in hexadecimal → 0x10.

The final physical silicon payload: 4A 01 44 C1 10. Five chaotic, incredibly dense bytes that encode a massive mathematical and memory routing operation.

11.3 The ARM64 (AArch64) Philosophy (RISC)

In stark contrast to x86's evolutionary baggage, ARM64 (AArch64) is a clean, modern, pure 64-bit RISC architecture. It powers the Apple M-Series, AWS Graviton servers, and every modern smartphone. It was designed from the ground up for massive superscalar pipeline throughput.

Fixed-Length Predictability

The defining rule of ARM64: Every single instruction is exactly 32 bits (4 bytes) long. There are no prefixes. There are no variable displacements.

This mathematical guarantee allows the Instruction Fetch (IF) unit to blindly slice an incoming 64-byte L1i cache line into exactly 16 instructions, instantly routing them to 16 parallel decoders without ever needing to inspect the contents. This solves the x86 length-decoding bottleneck entirely.

Strict Load-Store Architecture

ARM forbids direct memory mathematics. An ALU instruction (like ADD or MUL) can only operate on registers. If you want to increment a value in memory, you must explicitly encode the three physical $\mu\text{ops}$ in the software assembly:

; ARM64 Assembly Strict Load-Store
LDR X0, [X1]       ; Load from memory pointer X1 into register X0
ADD X0, X0, #5     ; Add 5 to X0
STR X0, [X1]       ; Store the result back to memory

While this inflates the binary size (decreasing Code Density), it radically simplifies the CPU's internal Out-of-Order Scheduler, as the hardware no longer needs to shatter complex CISC instructions.

The Orthogonal Register File

x86 registers have specific, hardcoded roles (e.g., RCX is used for loop counters, RDX is used for division remainders). ARM64 features a massive, Orthogonal Register File consisting of 31 identical, interchangeable 64-bit general-purpose registers (X0 to X30). Any register can be used for any operation, giving the compiler massive freedom to avoid WAW and WAR name dependencies natively without hardware renaming.

It also features a hardwired Zero Register (XZR). Reading XZR always yields 0. Writing to XZR acts as a bit-bucket (discarding the data), heavily utilized for evaluating comparison flags without allocating temporary registers.

11.4 Anatomy of an ARM64 Instruction (Bitfield Slicing)

Because ARM instructions are strictly 32 bits, they are parsed via mechanical bit-slicing rather than sequential byte parsing.

; ARM64 Data Processing Instruction
ADD X0, X1, X2, LSL #2

This instructs the ALU to take X2, Logical Shift Left (LSL) by 2 bits (effectively multiplying by 4), add it to X1, and store the result in X0.

The 32-bit physical layout is brutally simple:

  • Opcode (Bits 31-21): 11 bits identifying the exact operation (Data Processing, Branch, Load/Store).
  • Shift Amount (Bits 15-10): 6 bits encoding the inline bit-shift (LSL #2).
  • Rm / Source 2 (Bits 20-16): 5 bits identifying the second operand register (X2). 5 bits provides $2^5 = 32$ possible registers.
  • Rn / Source 1 (Bits 9-5): 5 bits identifying the first operand (X1).
  • Rd / Destination (Bits 4-0): 5 bits identifying the destination (X0).

The Immediate Encoding Dilemma & Literal Pools

Fixed 32-bit instructions introduce a severe mathematical paradox. If the instruction itself is 32 bits long, how do you load a 64-bit constant (like a massive memory pointer) into a register?

On x86, you just append an 8-byte immediate payload to the end of the opcode, resulting in a 10-byte instruction. ARM64 physically cannot do this. It solves the paradox using two techniques:

1. Move with Keep (MOVK): The compiler breaks the 64-bit constant into four 16-bit chunks and issues four sequential instructions, shifting them into place.

MOVZ X0, #0x1234, LSL #48  ; Load upper 16 bits
MOVK X0, #0x5678, LSL #32  ; Keep existing, load next 16 bits
MOVK X0, #0x9ABC, LSL #16
MOVK X0, #0xDEF0           ; Load final 16 bits

2. The Literal Pool (PC-Relative Load): If four instructions are too slow, the compiler embeds the raw 64-bit constant directly into the .text executable code segment (data mixed with instructions). The CPU uses a LDR X0, [PC, #offset] instruction to jump ahead, read the 64-bit constant from the code binary, and load it into the register. This is highly efficient but heavily pollutes the L1i instruction cache with non-executable data.

11.5 Architectural State & Calling Conventions (ABI)

The Application Binary Interface (ABI) is the software layer that sits directly on top of the ISA. When you write a C# or C++ function, the ABI dictates exactly how the caller passes arguments to the callee, and which registers must be preserved.

Volatile vs. Non-Volatile (Callee-Saved) Registers

If Function A calls Function B, Function B is legally allowed to overwrite Volatile registers. If Function A needs that data, it must save it to the Stack before the call. Conversely, Non-Volatile (Callee-Saved) registers are legally protected. If Function B wants to use them, Function B must push them to the Stack, execute its logic, and pop them back into their exact original state before returning.

The Cross-Platform Chaos (Windows vs. Linux/Mac)
This is the primary reason a compiled Windows .exe cannot run natively on Linux, even if both OSes use the exact same x86-64 CPU hardware. Their ABIs fundamentally disagree on how to pass function arguments across the silicon.

The Microsoft x64 ABI (Windows)

Microsoft enforces a strict, rigid calling convention for C/C++ and the .NET Core JIT on Windows.

  • Argument Passing: The first four integer/pointer arguments are strictly passed in RCX, RDX, R8, and R9. Floating-point arguments use XMM0 through XMM3. Any additional arguments are pushed to the physical Stack.
  • The Shadow Space: The caller is legally mandated to allocate 32 bytes (4 words) of empty, useless space on the Stack just before the call. This allows the callee to instantly dump RCX/RDX/R8/R9 into memory if it needs to free up those registers for internal math.
  • Non-Volatile Registers: RBX, RBP, RDI, RSI, R12-R15.

The System V AMD64 ABI (Linux, macOS, FreeBSD)

The Unix world optimized the x86-64 architecture differently, optimizing for heavy usage.

  • Argument Passing: The first six arguments are passed in registers: RDI, RSI, RDX, RCX, R8, R9.
  • No Shadow Space: Linux does not waste 32 bytes of stack memory per call.
  • The Red Zone: System V defines a 128-byte "Red Zone" directly below the Stack Pointer (RSP). A leaf function (a function that doesn't call any other functions) can legally write local variables into this zone without subtracting the RSP to allocate stack space, saving two ALU instructions per function call. Windows completely lacks this feature, triggering hardware interrupts if the Red Zone is touched.

11.6 ARM64 Calling Conventions (AAPCS64 vs Apple Silicon)

The standard ARM64 ABI is the AAPCS64 (ARM Architecture Procedure Call Standard). It exploits the massive 31-register orthogonal file.

  • Argument Passing: The first eight arguments are passed in X0 through X7.
  • Return Value: Passed in X0.
  • Callee-Saved: X19 through X28.

Apple Silicon ABI Deviations

When Apple migrated macOS from Intel to the M-Series ARM64 chips, they adopted the AAPCS64 but injected proprietary deviations. Most notably, Apple altered how Variadic Functions (like printf in C) handle argument passing, tightly coupling the ABI to their proprietary hardware mitigations for stack smashing, making standard Linux ARM64 binaries incompatible with Apple Silicon without translation.

The Hardware Cost of CALL: The Link Register Advantage

One of the most profound performance differences between x86 and ARM lies in how they handle function calls mechanically in silicon.

The x86 CALL Instruction:

call MyFunction  ; Pushes 8-byte RIP to RAM, jumps to target

On x86, every single function call is forced to interact with the Memory Access (MEM) stage. The CPU physically subtracts 8 from the RSP stack pointer, and executes a memory STORE operation to write the Return Address to the L1 Data Cache. When the function finishes, RET executes a memory LOAD to read it back. This generates massive, unnecessary cache traffic for simple helper functions.

The ARM BL (Branch and Link) Instruction:

BL MyFunction    ; Stores Return Address in Register X30, jumps

ARM natively reserves physical register X30 as the Link Register (LR). When a function is called, the CPU stores the 64-bit return address directly into X30 inside the ultra-fast Physical Register File (PRF). The MEM stage is completely bypassed. The L1 Data Cache is never touched.

If MyFunction is a "Leaf Function" (it does not call any other functions), it executes its logic and simply calls RET, which jumps back to the address in X30. Function calls on ARM are $O(1)$ register routing operations, drastically improving throughput and reducing power consumption in deep Object-Oriented call trees.

11.7 Addressing Modes & Array Iteration

The ISA dictates how the Execute stage's Address Generation Unit (AGU) computes physical memory pointers. How the architecture handles array iteration defines its loop efficiency.

x86-64 Stack Mechanics (Implicit Updates)

x86 utilizes implicit hardware registers. The push and pop instructions not only read/write memory but automatically decrement/increment the RSP (Stack Pointer) via internal ALU micro-ops.

push rax  ; 1. SUB RSP, 8   2. STORE [RSP], RAX

Because x86 CISC allows this, code density remains incredibly tight when manipulating the stack.

ARM64 Pre-Indexed & Post-Indexed Addressing

ARM completely lacks native PUSH and POP instructions. To emulate stack manipulation or array iteration, ARM utilizes hardware Write-Back addressing modes. The AGU not only calculates the pointer, but updates the base register in a single cycle.

; ARM64 Pre-Indexed Addressing (Emulating PUSH)
STR X0, [SP, #-16]!   ; Subtract 16 from SP, THEN store X0. 
                      ; The '!' indicates Write-Back to SP.

; ARM64 Post-Indexed Addressing (Array Iteration)
LDR X0, [X1], #8      ; Load memory at X1 into X0, THEN Add 8 to X1.

The Post-Indexed mode is a masterclass in Mechanical Sympathy. In a C# foreach loop traversing an array, the CPU fetches the current integer and automatically increments the array pointer to the next integer using a single hardware instruction, entirely eliminating the need for a separate ADD X1, #8 ALU instruction inside the hot loop.

11.8 The Decoder Physics & Apple's M-Series Advantage

We now arrive at the physical silicon limit that defines the modern CPU war. Why are Apple’s M-Series ARM chips (M1, M2, M3, M4) crushing traditional x86 processors in performance-per-watt and sustained Instruction-Level Parallelism (ILP)? The answer is found entirely in Decoder Physics.

The x86 Variable-Length Decoding Bottleneck

To build a superscalar CPU, you must feed the execution core with multiple instructions per clock cycle. If you want a 6-wide superscalar engine, your Front-End must fetch, inspect, and decode 6 instructions simultaneously every 0.2 nanoseconds.

On x86-64, because instructions are variable length (1 to 15 bytes), the hardware cannot know where instruction 1 ends and instruction 2 begins until it fully evaluates the opcode bytes. This requires a massive array of overlapping speculative length-decoders that check byte boundaries in parallel. Building this hardware for a 4-wide or 6-wide x86 decoder is an engineering nightmare that consumes massive amounts of power and silicon real estate. This is why Intel and AMD have struggled for a decade to push past 4-wide or 6-wide decoders without melting the die.

The Fixed-Length Decoupling Advantage

On ARM64, every instruction is strictly 4 bytes (32 bits). The Instruction Fetch unit does not need to guess instruction boundaries. It simply takes a 64-byte L1i cache line, cuts it into sixteen 4-byte chunks with absolute mathematical certainty, and feeds them directly into 8, 10, or 12 parallel decoders simultaneously.

Apple’s M-Series chips feature massive 8-wide and 10-wide decoders. They can flood the $\mu\text{op}$ Queue with up to 10 decoded instructions per clock cycle. This feeds the massive Out-of-Order core with an unconstrained torrent of work, allowing Apple silicon to achieve staggering IPC heights at a fraction of the thermal wattage of x86.

11.9 The Rosetta Stone: Side-by-Side Code Focus

To tie these architectural principles together, let us examine how a high-level C# loop compiling an array summation maps to raw x86-64 assembly versus ARM64 assembly.

// High-Level C# Target
long SumArray(long[] data, int length) {
    long sum = 0;
    for (int i = 0; i < length; i++) {
        sum += data[i];
    }
    return sum;
}

1. x86-64 Assembly (System V ABI - Linux/Mac)

; Inputs: RDI = data pointer, ESI = length
SumArray:
    xor rax, rax          ; sum = 0 (RAX is return register)
    xor r8d, r8d          ; i = 0 (R8D is loop counter)
.L_loop:
    cmp r8d, esi          ; Compare i against length
    jge .L_done           ; If i >= length, exit loop
    
    ; Load data[i] using SIB addressing [Base + Index * Scale]
    mov rdx, [rdi + r8*8] ; Fetch 8-byte integer from array
    add rax, rdx          ; sum += data[i]
    
    inc r8d               ; i++
    jmp .L_loop           ; Jump back to start
.L_done:
    ret                   ; Return sum in RAX

Observations: Notice the mix of explicit memory addressing (`[rdi + r8*8]`) and the explicit jump instructions (`jmp`) required to manage the loop control flow.

2. ARM64 Assembly (AAPCS64)

; Inputs: X0 = data pointer, W1 = length
SumArray:
    mov x2, #0            ; sum = 0 (X2 holds running sum)
    mov x3, #0            ; i = 0 (X3 holds loop index)
    sxtw x1, w1           ; Sign-extend length to 64-bit
.L_loop:
    cmp x3, x1            ; Compare i against length
    b.ge .L_done          ; Branch if Greater or Equal (Exit)
    
    ; Post-Indexed Addressing & Load
    ldr x4, [x0], #8      ; Load data[i] into X4, AND increment X0 by 8 instantly!
    add x2, x2, x4        ; sum += data[i]
    
    add x3, x3, #1        ; i++
    b .L_loop             ; Unconditional branch back
.L_done:
    mov x0, x2            ; Move sum into return register X0
    ret                   ; Return (Jump to Link Register X30)

Architectural Efficiency: Look at the ARM instruction ldr x4, [x0], #8. It performs the memory load and increments the pointer X0 in a single hardware cycle. Furthermore, the return statement simply calls RET, which uses the internal Link Register X30 without touching the physical stack in RAM. The ARM binary is cleaner, requires fewer register names, and executes with maximum pipeline density.

Prompt 1: x86 variable-length instructions (1-15 bytes) mean the hardware cannot know where an instruction ends without fully decoding it. Building parallel length-decoders to feed a 6-wide superscalar core requires massive, power-hungry silicon. ARM's fixed 32-bit length allows deterministic slicing of cache lines, enabling Apple to build massive 8-wide/10-wide decoders effortlessly.
Prompt 2: ModR/M routes register and memory operands. The SIB byte encodes Base + Index * Scale. The AGU uses this math engine to compute array pointers in 1 cycle. RISC architectures lack complex memory-addressing modes, requiring separate ADD and SHIFT instructions to achieve the exact same pointer calculation.
Prompt 3: The ABI defines calling conventions. Windows x64 uses RCX/RDX/R8/R9 with a mandatory 32-byte Shadow Space. Linux System V uses RDI/RSI/RDX/RCX/R8/R9 with a 128-byte Red Zone. Because argument registers and stack cleanup rules differ fundamentally, a Windows binary cannot resolve Linux system calls or register conventions natively.
Prompt 4: x86 CALL pushes RIP to the physical RAM stack via the MEM stage, interacting with the L1 Data Cache and generating cache traffic. ARM's BL stores the return address in the dedicated Link Register (X30) inside the ultra-fast PRF, completely bypassing RAM and enabling $O(1)$ leaf function returns.
Prompt 5: Modern x86 processors are CISC on the outside, RISC on the inside. Complex macro-instructions (like add qword [rcx], 5) are intercepted by hardware decoders and shattered into RISC-like micro-operations ($\mu\text{ops}$: LOAD, ADD, STORE) before entering the Out-of-Order execution core, allowing CISC binaries to run on RISC execution engines.
